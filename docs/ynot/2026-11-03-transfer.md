# Second consumer and three-arm transfer — 3 November 2026

A second development job runs on the same capability lifecycle, with holdout cases written by a separate agent and a current-DSPy baseline beside the direct one. Every arm solved both jobs with its first candidate and passed every holdout. Neither job separates the three approaches on correctness, model use or time. The useful result is a defect in how contracts were being written, found by the real boundary before any model call.

## The job

The strict structured-output normalisation in [`strict_schema_case.py`](../../examples/ynot/strict_schema_case.py) starts from a real failure: on 3 November the Codex CLI rejected an ordinary generated schema with HTTP 400 `invalid_json_schema` because `additionalProperties` was not `false` ([recorded observation](../../examples/ynot/cases/strict-structured-output-observation.json)). The repository's own adapter hand-writes this normalisation; MCP tool schemas need the same shape for strict clients. Seven host cases qualify a candidate. Six [holdouts](../../examples/ynot/cases/strict-structured-output-holdouts.json) were authored by a separate agent from the specification alone, with its reading of each silence recorded in a note. The agent never saw the control implementation, the host cases or the code.

## What the boundary found before the model ran

The first specification said the `required` list follows the original property order. The control implementation passed all seven host cases in the real Deno boundary and then failed all six holdouts on fresh-process reuse. The store canonicalises every payload and output as JSON with sorted keys, so property order does not survive `CapabilityStore.run`. The host cases happened to list properties alphabetically; the independent holdouts did not. The rule now sorts `required` by name and states that object key order is not significant. The separate author re-derived the holdouts under the amended rule. The [foundation guide](FOUNDATION.md) records the constraint for every future contract.

## Live results

All runs used `gpt-6-astra`, medium reasoning, through the existing Codex CLI login, with at most three candidate attempts and the same checks, boundary and allowances per arm. The DSPy arm is a plain `dspy.Predict` on the same engine with host feedback as an input field; no optimiser was run. Each arm saved its accepted code and reused it in a fresh process.

An earlier nullability run in direct-first order is retained as superseded evidence: its direct and YNOT arms passed (34.709 and 41.361 seconds, one call each); its DSPy arm produced an accepted candidate and then failed on a harness defect, saving a programme whose engine cannot be serialised. The programme is now saved without the engine. That run's model call counts towards the evening's use; its arm result is an infrastructure error, not a model failure.

Time includes model generation, qualification and fresh-process reuse. Provider token reports are retained as returned, cached-input fields included; no cash cost is inferred. The DSPy arm returned shorter outputs and finished a few seconds sooner in every run; it writes plain text in the adapter's field format rather than JSON-escaped source under an output schema. Three runs cannot establish that difference or any general overhead.

## Decision

Both bounded jobs are too easy to discriminate: one competent model call solves each, and the lifecycle's records, policy checks and revocation add no measured value here. The second consumer earned its place by exposing the canonicalisation rule and by making a separate author's cases part of the method. The next evaluation needs jobs where first candidates fail, transfer is uncertain and accumulated capabilities can be selected or repaired, with the same three arms and equal reuse. Store accumulation across jobs is still not exercised. The tenfold target remains a target. Nothing here supports publishing an advance.
