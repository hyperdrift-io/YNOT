# Track A: real fixtures, hidden tests, two models — 6 November 2026

Three arms ran six development jobs on two models, in two orders, three times each: 216 job records, 18 arm runs per model. The three new jobs use fixtures the model never sees and did not write: the fleet's own MCP tool schemas, the official draft-04 test suite with its instance verdicts, and whole public OpenAPI documents. `gpt-6-astra` solved every job first time in every arm and passed every holdout, as on 3 November. `gpt-6-luna` at low reasoning produced the first failures of this study: second attempts, three jobs never accepted, and accepted candidates that failed hidden holdouts. On that model the direct baseline, plain DSPy and YNOT finished level, with YNOT no better on any measure. The pre-registered reading for that outcome applies: the orchestration layer leaves the pitch; the store stays as a library feature.

## What was added

Three jobs, each with a real observed failure and expected outputs derived twice, by the deterministic control and by an independent reader of the specification who saw no code; the two derivations agreed on every fixture.

- [`mcp-tool-strict`](../../examples/ynot/mcp_tools_case.py): the 36 tools of `crunch-accounting-mcp`, `deputy-workforce-mcp` and Traction define 29 distinct input schemas, listed from the servers themselves. Eight are host cases, 21 are holdouts. The observed failure is the strict client's live rejection of one fleet schema as emitted.
- [`draft04-suite-migration`](../../examples/ynot/suite_migration_case.py): 146 usable groups of [JSON-Schema-Test-Suite](https://github.com/json-schema-org/JSON-Schema-Test-Suite) draft-04, ten host cases, 136 holdouts. Fifteen groups are excluded and listed with the reason: remote references, and reference or base-URI semantics that changed between the drafts and have no mechanical equivalent under the written rules. Each holdout has a second measure: the output must validate as 2020-12 and give every instance the same verdict as the original.
- [`openapi-components-strict`](../../examples/ynot/openapi_document_case.py): 21 public OpenAPI 3.0 documents whose component schemas are self-contained and acyclic, from learn.openapis.org and the APIs.guru directory. Five host cases, 16 holdouts. The job resolves references within the document, converts nullability and makes every component strict; the second measure is a strictness lint independent of wording.

The [runner](../../examples/ynot/capability_accumulation.py) records the second measure beside exact matching on holdouts. Each arm run took the six jobs in order: strict normalisation, fleet schemas, migration, suite migration, nullability, whole documents, so the earlier capability was in the catalogue when its real-fixture successor arrived.

## What failed, and why

Every failed holdout of an accepted `gpt-6-luna` candidate was re-run and classified.

- **Wording, behaviour preserved.** Twelve of the draft-04 misses add an `items` keyword beside `prefixItems` where the rules say none. The output validates and gives every instance the same verdict. This is the case the second measure was built for: an exact-match holdout fails, the work is still usable.
- **Defects the host cases did not catch.** `$ref` strings and `id` keys inside `definitions` left unrewritten when nested two levels down; `additionalItems` kept beside list items; a boolean `exclusiveMinimum` inside a list of item schemas not converted. Each produces an unresolvable pointer or a rejected schema. The same rule is applied correctly one level up in the same candidate.
- **A nested object's own `required` list ignored.** One YNOT candidate made inner required properties nullable on two fleet tools because it read the root's required list for every level.
- **Never accepted.** YNOT's strict job in one run: the candidate copied the input's `required` after setting it, so its result depended on key order, the rule recorded on 3 November. Three attempts, each told only the failing indices and `unexpected_output`, repeated the defect. DSPy's whole-document job and migration job each failed three times in one run on one host case.

The feedback a failed case returns is an index and a word. The frontier model never needed more; the weaker model repaired on it in nine of twelve second attempts and otherwise repeated itself. Richer feedback after a failure, at least the failing case's input and the shape of the difference, is the first amendment to the design.

## The DSPy arm had to be fixed before it could be measured

In the first matrix `gpt-6-luna` accepted 3 of 36 DSPy jobs over 106 calls. The cause was format, not development: the model writes the adapter's closing marker as `[[ ## completed ##]]`, DSPy's `ChatAdapter` then leaves it inside the last field, and the runner saw both a source and a composition. Tolerating the misspelt marker and rerunning the six cells gave the DSPy row above. The direct and YNOT arms never met this because the provider enforces their JSON output schema. Both runs are in the evidence; the comparison uses the parsed one. A baseline whose format breaks on the weaker model would have flattered the others.

## Reading against the pre-registered readings

- *Weaker model with YNOT matches the frontier model's accepted work at under half the tokens.* No. On `gpt-6-luna` YNOT accepted 1,112 holdout cases for 24,711 output tokens; `gpt-6-astra` direct accepted 1,134 for 22,027. More tokens, less work. The economic claim has no first supporting result.
- *YNOT prevents stale reuse the baselines commit.* Not tested here; that is Track B.
- *Arms remain tied on the weaker model too.* Yes. Direct 36 accepted and 34 first-time, YNOT 35 and 30, DSPy 34 and 28, on identical prompts; the only systematic difference between arms starts after a failure, so first-attempt gaps of this size over six runs are chance. Where YNOT differs it is behind, not ahead. Per the design: retire the orchestration layer from the pitch and keep the store as a library feature.
- Every cell has three repeats in each order, so these are findings under the design's own rule, with the caveat that six runs per cell resolve large effects only.

Real fixtures did what the design asked of them. Hidden holdouts caught defects that eight or ten host cases passed; the behaviour measure separated wording from damage; the weaker model showed where repair and feedback matter. They did not make the frontier model fail, and nothing here moves the frontier-model result of 3 November.

## Decision

Keep the three Track A jobs and the behaviour measures; they are the first fixtures in this repository that discriminate anything. Amend the design: richer feedback after a failed host case, and a DSPy arm whose parsing is checked on the weaker model before a matrix runs. Run Track B next on both models; it is the only place the controls can still show value beyond bookkeeping. The direction text no longer claims an orchestration advantage. No article revision, claim or publication follows from this.
