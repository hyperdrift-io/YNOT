# YNOT

YNOT is an Orchestra offering for an AI-native organisation that takes on useful work, contracts supervisors, and assembles capable agents according to the work and capacity available. Each supervisor remains accountable for delivery against a shared mission. Hyperdrift is the company building the offering; internal use is part of developing it, not a customer relationship.

YNOT is an experimental DSPy fork for programmable, evaluable supervision: a programme can select and configure workers, adapt to observed capacity and retain responsibility for the outcome. This serves DSPy's purpose of programming and optimising language-model systems. The claim to test is better task completion, recovery or cost with less human coordination; a fork and extra agents do not establish that improvement. [DSPy optimisation model](https://github.com/stanfordnlp/dspy/blob/25162c4fc05c2d2d019b0ffb5b6b2a9f315ec007/docs/docs/learn/optimization/optimizers.md).

DSPy already supplies modules, agents and optimisers. Use them to make the first application work; change the core only when a reproduced limitation prevents the needed behaviour. YNOT preserves DSPy's history and MIT attribution. The fork and planning documents exist; the application, public admission service and autonomous execution system are not operating yet.

The [mission](MISSION.md) is to give founders the delivery capacity to turn a business problem into a working improvement without managing every specialist and handoff. Our first Orchestra application is helping a customer reach their first useful result in an existing product. This replaces the earlier DSPy-contribution demonstration as the driver of implementation.

## First outcome

Complete one evidence-backed customer-journey improvement in an existing application. A supervisor owns diagnosis, delivery, verification and the result to measure. Start with one worker; introduce another for a needed capability or a controlled availability change. A replacement must continue from the retained evidence without restarting the investigation or exceeding the allocation.

The founder's trial-onboarding request in the mission is an illustrative application. Tonight's internal run needs a real baseline and a selected supported obstruction; no conversion failure or customer outcome is established yet.

A work agreement means a machine-readable mandate: mission version, goal, deliverable, acceptance evidence, permitted actions, resource allowance, expiry and stop condition. It is not initially a financial or blockchain contract.

## First complete application and comparison

A founder commissions one useful improvement: “People start a trial but get stuck before completing their first job. Find the obstruction and fix it.” The example is illustrative. Select an existing application, name the actual journey and inspect the evidence before implementation. If there is no supported obstruction, return that finding and choose the next justified action.

The first programme can configure instructions and demonstrations at a step boundary, evaluate the candidate and retain the previous configuration if it fails. Do not optimise during every request by default. Use observed failures to justify a small, separately budgeted optimisation, then evaluate on examples it did not train on. DSPy's optimisers already support metric-driven improvement; applying one is not a new YNOT invention.

Run the first job end to end in one session: commission, baseline, YNOT execution, review and comparison. Each run starts from the same clean application snapshot and initial evidence, without access to the other run's patch or investigation. Apply the same labelled availability control to both systems. Count supervisor and worker calls within YNOT's total allowance. A single job and controlled repeats establish a demonstration, not a general superiority claim. If upstream DSPy gives the same useful result more simply, retain the useful application and drop the added mechanism. Add wallet admission and network services after a concrete external-participation need.

The first routing rule should be understandable: satisfy capability and permission requirements, check current capacity, then choose using relevant delivery evidence and resource cost. Unknown capacity or competence stays unknown. Do not start with an invented universal reputation score or an agent committee for every decision.

A supervisor may recruit, delegate and reassign within its work agreement. Delegation cannot increase permissions or the resource allowance. The execution host enforces limits; a prompt describing them is not enforcement. Reassignment does not guarantee exactly-once external effects: the first task must use reversible repository work, with task claims and result acceptance checked centrally.

## Decide what deserves a merge

Ask who benefits, how the change advances the mission, what observable result improves and what continuing complexity it adds. Flag unrelated work, abstractions without a consumer and speculative edge cases consuming the budget. Describe evidence and behaviour without attributing ego. An uncommon case can still matter when its consequences justify the effort.

Research is optional evidence. Reputation can inform assignment but cannot waive acceptance checks. Keep the evaluator and acceptance policy outside the candidate's authority. Contributors do not approve their own changes. Routine qualifying merges may be automated once the execution boundary and checks are enforced; they do not need a person to relay every agent exchange.

Use existing DSPy APIs before creating a new core abstraction. Current DSPy already supports cloning modules, changing signature instructions, per-call demonstrations and prediction configuration. The first contribution may therefore be a useful orchestration example with regressions rather than a core API change.

Reasoning continuity remains a candidate contribution. Existing offline evidence preserves synthetic continuation state through save/load; it does not prove live-provider compatibility. Review it against a real supervisor/worker handoff before merging. It is not a prerequisite for task-specific configuration, and should not delay the first supervised run. No upstream acceptance or rejection of our implementation is claimed.

## Admission and public trust

Owned, authorised development sessions can prepare this experiment before public admission exists. They are not wallet-verified network members. Public participants must prove wallet control and receive bounded, revocable task authority. A signature establishes control; useful, independently checked work establishes competence.

Keep agent identity, operator, programme/configuration version, work, evidence and later corrections linked. Distinct wallets or models do not establish independent operators. A new operator or configuration does not silently inherit the prior version's trust. Public receipts preserve authorship separately from validation and omit private inputs.

ERC-8004 and A2A remain interoperability possibilities. Web3, payments, ZK proofs and a new storage network are not prerequisites for the first run. The existing protocol comparison informs later admission; no chain has been selected. Do not load unreviewed executable programmes or give submitted code privileged workflow credentials.

## Publication and useful learning

Orchestra will explain the work through a proposed daily sequence beginning 30 October 2026: why YNOT; DSPy's programme model; one actual supervised contribution; and evidence-backed agent trust. Existing DSPy drafts should be reused. Release claims must match what has been demonstrated; use the actual publication date and preserve the destination's exact-copy review.

The near-term measure is a person completing a supported journey after a justified improvement, with delivery cost, coordination effort and unresolved findings recorded. Internal controls and live customer outcomes remain distinct. Later measures are independent use, less coordination effort, reliable recovery and successful reuse by another organisation. Forks, merges and article views alone do not establish those outcomes.
