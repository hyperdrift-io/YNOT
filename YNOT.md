# YNOT

YNOT is an experimental DSPy fork and an Orchestra offering for supervised agent work. A founder commissions a result; the supervisor assembles existing capabilities, configures specialists as the mission develops and stays accountable for delivery. The [mission](MISSION.md) is the source for what should improve and how we judge it.

DSPy supplies programmable modules, agents and metric-driven optimisation. YNOT develops and tests improvements for supervised execution. A useful application comes first; a core change earns its place through a reproduced limitation. DSPy's history and MIT attribution are preserved. The [controlled runtime-specialist example](examples/ynot/README.md) now creates and executes real DSPy ReAct workers from specifications generated during the run. Its default responses and sources are scripted and fictional; live prospect research, the Apollo integration and a quality advantage remain unverified.

## First application

**Find one customer worth pursuing.** Input: the offer, website and an example of a good customer. Output: a supported opportunity, why it fits, a dated reason to investigate now, remaining uncertainty and a useful conversation starter. The next commercial step is “Help me pursue this opportunity” through Orchestra's existing enquiry flow.

This is an outcome to test, not a promise of a sale. Start with B2B software and service founders with a working offer. Run the first internal mission on Orchestra's own offer. Hyperdrift builds and validates the service; it is not a customer.

## Complement the ecosystem

| Existing capability | Reuse | YNOT's contribution to test |
| --- | --- | --- |
| Prospect and sales research | Apollo's documented APIs or approved agent interface. | Decide which question to ask, connect findings to the founder's offer, investigate gaps and assess the result. |
| Language-model programmes | DSPy modules, agents and optimisers. | Configure and evaluate task-specific specialist behaviour during a mission. |
| Execution and delegation | Existing runtimes where they supply the needed boundary and handoff. | Preserve the mission, evidence and remaining allowance across a justified change in approach or available capacity. |
| Commercial relationship | Traction and the existing Orchestra enquiry workflow. | Bring a usable result and next action into the existing relationship, rather than create another CRM. |

Apollo already offers agent-driven prospecting and research. Deep Agents documents dynamic subagents, and Relevance AI provides workforce routing and tools. We should use or contribute to these capabilities where they fit. Agent creation, orchestration and handoffs are not market-uniqueness claims. The proposed differentiation is evaluated adaptation in an accountable Orchestra service; a comparison must establish its value. Sources: [Apollo assistant APIs](https://docs.apollo.io/reference/use%20the%20ai%20assistant), [Deep Agents](https://docs.langchain.com/oss/python/deepagents/dynamic-subagents), [Relevance AI Workforces](https://relevanceai.com/docs/get-started/core-concepts/workforces).

## Configure the expertise the evidence calls for

Start with the mission and an approved capability catalogue, rather than a compulsory roster of specialist roles. A supervisor identifies a gap and proposes a worker configuration: purpose, task context, instructions, allowed tools, permitted model and completion criteria. The host validates the configuration, creates the DSPy programme and executes it. A role description alone is not a working specialist.

New evidence may justify another configuration, a different service or a replacement worker. Carry completed findings and source references forward. Retain the prior configuration when a proposed change fails its checks. Preserve the original mission, authority and remaining allocation throughout.

The candidate cannot weaken the minimum acceptance checks, grant itself tools or enlarge its budget. Runtime limits must be enforced outside model judgement. Reuse a simpler existing programme when it gives the same useful result. Stored configurations can inform later work only with their provenance and evaluation limits; private customer context must not silently transfer.

## First complete run and comparison

1. **Define the commission.** Fix the offer, customer-fit criteria, acceptable evidence, permitted services, resource allowance and stop condition. Missing provider access remains visible.
2. **Establish a baseline.** Run a competent upstream-DSPy or existing service workflow. Use the same model access, tools, evidence and total allowance. Include setup and optimisation cost.
3. **Execute YNOT.** Show a specialist created after a real evidence gap, its validated configuration, actual execution and how the finding changes the next decision.
4. **Check the result.** Verify sources and relevance separately from writing quality. Return uncertainty or no suitable opportunity when the evidence does not support one. Never fill a quota by inventing fit or intent.
5. **Test adaptation.** Apply the same labelled availability control to both systems. Verify that a replacement preserves evidence and the remaining allowance. Keep final comparison inputs separate from development examples.
6. **Decide what deserves investment.** Assess the founder's judgement of usefulness, completion, factual support, coordination, elapsed time and cost. Retain the simpler approach if the added mechanism supplies no worthwhile benefit.

Each comparison starts from the same initial evidence without access to the other run's investigation. Count supervisor and worker calls within the total allowance. A scripted fixture proves control flow; a live run is needed to assess research quality. Neither one run nor an internal demonstration establishes general superiority, external adoption or customer demand.

Review the actual change, run meaningful checks and commit directly to the authorised main branch. Preserve authorship. Use each application's established release path and verify a served result when released. No upstream PR is part of this internal delivery.

## Provider boundaries and later participation

Apollo's assistant uses the acting user's permissions: restricting an API key to assistant endpoints does not restrict the actions the assistant can perform. An initial integration must use explicitly permitted research operations or a sufficiently restricted provider identity; a prompt asking it to be read-only is not an access boundary. Provider costs and writes need a known authorised policy. No Apollo connection or permission has been activated here. [Apollo permission model](https://docs.apollo.io/reference/use%20the%20ai%20assistant).

Owned development sessions can prepare the experiment before public admission exists; they are not verified network members. External participants will need verified-wallet control, bounded revocable task authority and isolated execution. A signature identifies control, while useful independently checked work establishes competence. Distinct wallets or models do not prove independent operators.

ERC-8004, A2A and Web3 remain interoperability possibilities. Wallet infrastructure, payments and ZK proofs are not prerequisites for the first internal run. Reasoning continuity remains a candidate where a real handoff demonstrates the need; it does not block task-specific configuration.

## Explain the result

Orchestra's articles should show what the programme configured, why it changed, what was executed and what the result supports. The future proposition is an organisation whose expertise adapts to the job while responsibility stays with its mission. Treat this as a direction to prove, credit the projects that make it possible and publish actual results with their limits.
